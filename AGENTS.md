# AGENTS.md

## Project

Это frontend приложения «Запись на звонок» — упрощённый сервис бронирования времени по мотивам Cal.com.

В приложении:
- нет авторизации;
- нет личных кабинетов;
- есть один заранее заданный владелец календаря;
- гость выбирает тип события, дату, свободный слот и создаёт бронирование;
- владелец смотрит предстоящие встречи и управляет типами событий.

## Frontend stack

Используем:
- TypeScript;
- Vite;
- React;
- Tailwind CSS;
- shadcn/ui;
- React Router;
- Prism для mock API во время разработки.

## Architecture

Используем упрощённый FSD:

- `app/` — роутинг, провайдеры, глобальные стили;
- `pages/` — страницы;
- `widgets/` — крупные UI-блоки;
- `features/` — пользовательские действия;
- `entities/` — бизнес-сущности;
- `shared/` — общий код, UI, API client, utils.

## API rules

- API-контракт лежит в `docs/call_booking_api.tsp`.
- Frontend должен работать только через API по контракту.
- Нельзя выдумывать endpoint'ы.
- Нельзя выдумывать поля request/response.
- API base URL должен браться из `VITE_API_BASE_URL`.
- Все API-запросы должны идти через `shared/api`.
- React-компоненты не должны напрямую вызывать `fetch` или `axios`.
- Моковые данные внутри React-компонентов запрещены.
- Во время разработки можно использовать Prism mock server.
- Код должен работать и с Prism, и с отдельно запущенным backend.

## UI rules

Интерфейс должен быть простым и аккуратным:

- светлый фон;
- белые карточки;
- тонкие border;
- скругления;
- оранжевая primary-кнопка;
- много воздуха;
- адаптивность для desktop и mobile.

## Pages

Публичные страницы:

- `/` — главная;
- `/book` — выбор типа события;
- `/book/:eventTypeId` — выбор даты и слота;
- `/book/:eventTypeId/confirm` — подтверждение бронирования;
- `/book/success` — успешная запись.

Админка:

- `/admin` — список предстоящих встреч;
- `/admin/event-types` — управление типами событий.

## Development workflow

Работай маленькими шагами.

Перед изменениями:
1. Изучи задачу.
2. Найди релевантные файлы.
3. Проверь API-контракт.
4. Скажи краткий план.

После изменений:
1. Покажи, какие файлы изменены.
2. Запусти доступные проверки:
    - `npm run build`;
    - `npm run lint`, если есть;
    - `npm run typecheck`, если есть.
3. Если проверка не проходит, исправь проблему или явно объясни, почему не смог.

## Review rules

При ревью проверяй:

- задача выполнена без лишних изменений;
- нет моковых данных в компонентах;
- нет прямого `fetch`/`axios` в компонентах;
- API-запросы идут через `shared/api`;
- endpoint'ы соответствуют `docs/call_booking_api.tsp`;
- есть loading/error/empty states для API-страниц;
- disabled states работают правильно;
- без выбранного слота нельзя продолжить;
- занятый слот нельзя выбрать;
- авторизация не добавлена;
- protected routes не добавлены;
- UI адаптивен;
- компоненты не стали слишком большими.

## Important

Не переписывай весь проект без необходимости.
Не делай несколько крупных задач за один раз.
Если контракта не хватает — не выдумывай API, а явно напиши, чего не хватает.
